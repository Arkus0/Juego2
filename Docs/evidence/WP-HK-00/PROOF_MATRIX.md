# WP-HK-00 — Proof obligation matrix

Binding standard: `Docs/engineering/FOUNDATIONAL_PROOF_STANDARD.md`.

One row per acceptance criterion in `Docs/workpacks/HK/WP-HK-00.md`. "Positive
evidence" names what shows the criterion holds; "negative control" names the
injected defect that must turn the named check red. Every check identifier below
is asserted by name in `scripts/self-attacks/run-self-attacks.sh`, so a control
that stopped being causal fails the suite instead of passing quietly.

Reproduce everything with:

```bash
bash scripts/proof.sh                      # preflight, static, effective, compiler, tests, inventory
bash scripts/self-attacks/run-self-attacks.sh   # every negative control, red then green
```

## Matrix

| Proof obligation | Completeness argument | Positive evidence | Negative control / attack | Result | Residual risk |
|---|---|---|---|---|---|
| **A1.** Canonical product source has single ownership; no copied implementation and no linked/cherry-picked product files in alternate projects. | Ownership is decided for *every* `.cs` under the scanned roots, not for a sample: the file set is enumerated from disk, mapped to the owning project directory, and then cross-checked against three independent views of what each project compiles (evaluated `Compile` items, portable-PDB documents, real `csc` source list). A file compiled by two projects appears twice in those views and is reported. | `inventory/sources.json` (30 files, each with owner, class and SHA-256, all `compiledStatically` and `compiledEffectively`); proof phases `static`, `effective`, `compiler` green in `scripts/proof.sh`. | `duplicate-source-ownership` (link one file into a second assembly, build stays green) → `HK00-SOURCE-DUPLICATE-OWNERSHIP`, `HK00-SOURCE-FOREIGN-COMPILE-ITEM`, `HK00-SOURCE-FOREIGN-COMPILED-EFFECTIVE`; `duplicate-source-type-conflict` → same checks plus compiler error CS0433. | PASS | Non-`.cs` production inputs (`.resx`, generated code from future source generators) are not yet classified; none exist today and any generated file that is not on the expected-generated allow-list is reported (`HK00-SOURCE-UNEXPECTED-GENERATED`). |
| **A2.** Portable libraries target a Unity-compatible contract (`netstandard2.1`, C# 9); host/tests may use pinned .NET 8. | The contract is a per-class property set in `kernel-manifest.json`, compared against *evaluated* MSBuild values for every project (not project-file text), against the `TargetFrameworkAttribute` emitted into every built assembly, and against `/langversion` on the real compiler command line. | `inventory/projects.json` (6 portable-kernel projects at `netstandard2.1`/`9.0`, host+tooling+tests at `net8.0`); `EffectiveAssemblyTests.PortableKernelAssemblyTargetsNetStandard21`. | `toolchain-property-drift` (`LangVersion` → `latest`) → `HK00-TOOLCHAIN-PROPERTY`. | PASS | `netstandard2.1` compatibility with a specific future Unity version is asserted by the framework contract, not by an actual Unity import; that check belongs to H1. |
| **A3.** No UnityEngine, UnityEditor, DFU or game-content dependencies in the portable kernel. | Three layers are checked, not a name denylist over source text: declared references and packages, the `AssemblyRef` table of every built kernel assembly, and every `/reference:` the compiler actually received. An engine type can only be used if it is referenced, and a reference cannot hide from the metadata table. | Proof phases green; `EffectiveAssemblyTests.NoKernelAssemblyReferencesAForbiddenEngineAssembly`; `NamePatternMatcherTests.ManifestPatternsCoverTheDocumentedForbiddenSet`. | `forbidden-engine-dependency` (real `UnityEngine` stub project referenced and used from `Arkus.Game.World`) → `HK00-ENGINE-DEP-STATIC` + `HK00-ENGINE-DEP-EFFECTIVE`; `forbidden-engine-package` → `HK00-ENGINE-DEP-STATIC` + `HK00-PACKAGE-FORBIDDEN`. | PASS | The forbidden-name list is a list; an engine shipped under an unrelated assembly name would not match it. The structural guards behind it (no NuGet dependencies in production classes, no raw assembly references, declared-edge equality) are what actually bound the reference surface. |
| **A4.** Dependency graph is mechanically checked and acyclic. | The declared graph and the graph derived from project files are compared edge by edge in both directions (undeclared and missing edges), and both are cycle-checked. The built assemblies are then required to reference exactly the declared set — every declared edge must be exercised, and no undeclared kernel reference may appear. `DisableTransitiveProjectReferences` makes the declared edges the compile-time surface. | `inventory/graph.json` (20 declared edges, 20 project-reference edges, 20 effective assembly-reference edges); `DependencyGraphTests`; `EffectiveAssemblyTests.RuntimeDoesNotReachPastAuthoringAndValidation`. | `dependency-cycle` (Core → World back-edge) → `HK00-GRAPH-CYCLE` + `HK00-GRAPH-UNDECLARED-EDGE`, and the build itself fails; `layering-back-edge` (Runtime → Core) → `HK00-GRAPH-UNDECLARED-EDGE` + `HK00-REF-UNDECLARED-EFFECTIVE`. | PASS | Reference-level layering does not constrain runtime composition through reflection; nothing in the kernel uses reflection today. |
| **A5.** SDK/toolchain is pinned; clean restore/build/test works headlessly on Linux CI. | The pin is compared three ways: `global.json` must equal the manifest pin, the roll-forward policy must be narrow enough by a rule that lives in tooling code, and the running SDK must satisfy it. Restore runs in `--locked-mode` against committed lock files; the whole pipeline is one script that CI runs unchanged. | `scripts/proof.sh` green locally on SDK 8.0.131 and in CI, where the pin selected 8.0.130 out of twelve SDKs installed on the runner (8.0.100 through 10.0.400) and both runs produced byte-identical inventories; `SdkPinRulesTests` (9 cases incl. feature-band and prerelease rejection); headless host smoke test prints the composed kernel. | `toolchain-pin-loosened` (`rollForward` → `latestMajor`) → `HK00-TOOLCHAIN-SDK-PIN`. | PASS | The pin fixes the feature band, not the exact patch, so two runs can use different `8.0.1xx` patches; the exact SDK of each run is recorded in `artifacts/proof/report.json`. |
| **A6.** Warnings-as-errors for canonical kernel projects. | Checked as a declared property (evaluated MSBuild), as the actual `/warnaserror+` switch on the compiler command line, and demonstrated end to end by introducing a real warning and requiring the build to fail. Suppressions are constrained to a manifest allow-list on both the evaluated `NoWarn` and the compiler's `/nowarn`. | Proof phases green with zero suppressions outside `1701;1702`; solution builds with 0 warnings. | `warnings-as-errors-neutralised` → `HK00-TOOLCHAIN-PROPERTY`; `toolchain-option-mutated-at-build-time` (switched off *after* evaluation) → `HK00-COMPILER-OPTION` while `HK00-TOOLCHAIN-PROPERTY` is required to stay quiet; `warning-suppression-added` → `HK00-TOOLCHAIN-SUPPRESSION`; `effective-warning-as-error` → build fails with CS0219. | PASS | Analyzer rule sets can still change which warnings exist at all; the analyzer set is pinned only by the SDK feature band. |
| **A7.** CI fails closed if a required project/test/proof tool is absent. | The preflight runs *before* the solution build, from the manifest's required-file, required-project, required-test-project and required-proof-tool lists, and additionally requires every classified project to be in the solution so a solution build cannot silently skip one. The proof tool separates "findings" (exit 1) from "could not complete" (exit 2), and CI treats both as failure. | `scripts/proof.sh` preflight step; CI job step "Fail closed if a required proof input is absent". | `required-project-deleted` → `HK00-PREFLIGHT-PROJECT-MISSING`; `proof-tool-deleted` → `HK00-PREFLIGHT-PROOF-TOOL-MISSING`. | PASS | A deliberately corrupted proof tool that reports green is out of scope for mechanical detection; the tool's own logic is covered by unit tests and its findings are reproducible by an independent reviewer. |
| **A8.** Source/project inventories are generated mechanically; unowned/unclassified production `.cs` count is zero. | Inventories are produced by the same run that performs the checks, from the same data, and contain no environment-specific values; CI regenerates them and fails on any diff, so a stale inventory cannot accompany a passing claim. | `inventory/sources.json`: `productionSourceCount: 22`, `unclassifiedProductionSourceCount: 0`, `unclassifiedSources: []`; CI step "Fail if the generated inventory drifted". | `unclassified-production-source` → `HK00-SOURCE-UNCLASSIFIED`. | PASS | The inventory covers `.cs` under the declared scan roots; a production source placed outside every scan root would be invisible to it, though it could not be compiled into a classified project without tripping A1. |
| **A9.** Effective compiler inputs are inspectable enough to prove owned source is what is actually compiled; static project checks are defence in depth. | For every project the owned file set is compared against the portable-PDB document table *and* the real `csc` source list, and each compiled document's SHA-256 is compared with the file on disk, so "compiled" means this exact content. Build-generated sources must match an expected-generated allow-list. | Proof `effective` and `compiler` phases green; `EffectiveAssemblyTests.CompiledSourceMatchesTheFilesOnDisk`; `inventory/sources.json` marks every owned file `compiledEffectively`. | `source-excluded-from-compilation` → `HK00-SOURCE-NOT-COMPILED-STATIC` + `HK00-SOURCE-NOT-COMPILED-EFFECTIVE`; `source-excluded-by-build-target` → `HK00-SOURCE-NOT-COMPILED-EFFECTIVE` **while the static check is required to stay quiet**, which is the direct evidence that static checks are not the completeness argument; `hidden-generated-source` → `HK00-SOURCE-UNEXPECTED-GENERATED`. | PASS | The oracles describe the build that produced the inspected outputs; a different machine could produce different outputs, which is why CI re-runs the whole pipeline from a clean checkout at the candidate SHA. |
