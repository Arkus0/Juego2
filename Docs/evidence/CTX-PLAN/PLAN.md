# CTX programme plan — context efficiency without quality loss

Mode: PROCESS_ONLY planning only
Baseline main: `e388f6e3c9d42e89418bd8877ed36fcbcf6d2aaa`

## Problem

Juego2 has accumulated enough accepted history, evidence and role protocol that fresh sessions can spend substantial attention reconstructing facts that are either repeated, already accepted, irrelevant to the current role, or available more precisely from live GitHub. The result is not only token cost: excessive irrelevant context can make ownership, predecessor and current-state reasoning noisier.

The optimization target is therefore **context precision**, not minimum context.

## Product-quality invariant

No CTX workpack may save context by:

- weakening a workpack DoD;
- reducing exact-SHA evidence requirements where they already apply;
- removing independent Reviewer judgment;
- trusting Worker summaries as proof;
- hiding a cross-track gate;
- making a stale summary/index authoritative;
- deleting accepted evidence;
- making H1's local executor decide architecture/repair semantics.

If a compact view is insufficient, the role must read more.

## Why three workpacks

### CTX-01: selection

Risk owned: deciding what to load first without omitting material context.

Immediate benefit: subsequent sessions stop mechanically reading broad unrelated surfaces.

### CTX-02: semantic compression

Risk owned: compacting accepted predecessor guarantees without losing asymmetric/conditional semantics or reopening conditions.

This must come after CTX-01 because safe compression requires a defined escalation/authority model.

### CTX-03: representation and closure

Risk owned: replacing duplicated state/evidence/history prose with structured/derived surfaces without creating a new source-of-truth problem.

This must come last because DocSync/history/evidence representation should consume the accepted routing and capsule models.

## Why not one giant optimization PR

A single PR would force one Reviewer to validate three independently dangerous questions:

1. can role context be safely narrowed at bootstrap?
2. can predecessor contracts be safely summarized?
3. can evidence/history/state be safely restructured?

A PASS on one cannot establish the others. The three-WP split preserves causal review boundaries.

## Why not more WPs

Metrics, handoff compaction, ROADMAP history separation and structured evidence are coupled in the same repeated-state/representation claim and are closed together in CTX-03. Splitting each into a separate administrative WP would increase ceremony without a distinct product/process truth boundary.

## Execution strategy

The plan is intentionally front-loaded for savings:

```text
plan PASS
  -> CTX-01 immediately
  -> all following sessions can use its boot profiles
  -> CTX-02
  -> CTX-03 + measured closure
```

No local Unity execution is required for CTX. The user can complete the process track remotely before starting the planned H1 local phase.

## Baseline observations to preserve for measurement

Before CTX:

- exact-WP Worker startup convention broadly names `AGENTS.md`, `Docs/ROADMAP.md`, exact WP, Worker protocol and applicable proof material before predecessor reconstruction;
- session handoff contains a broad fixed read-first list;
- long accepted history lives in normal planning surfaces;
- predecessor guarantees are reconstructed repeatedly from original WP/PASS/proof/residual prose;
- PR bodies and DocSync surfaces repeat accepted SHAs/results across several documents;
- live GitHub can advance before a narrative summary is reconciled, so a fresh session must already know not to trust prose state blindly.

CTX-03 will compare representative post-CTX bootstrap selection against this baseline. The objective is fewer irrelevant/duplicated reads with **zero lost material obligations**, not an arbitrary minimum token number.

## Non-blocking relationship to product tracks

CTX changes process/navigation only. It does not semantically block H1/CITY/PA. Human execution priority is nevertheless to finish CTX-01 before the next expensive local H1 Worker so later sessions immediately benefit from the accepted routing model.
