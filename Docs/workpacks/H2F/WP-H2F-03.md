# WP-H2F-03 — Integrated compatibility + AI-authoring benchmark

Status: **PROPOSED / NOT_STARTED**  
Class: `PRODUCT_CHECKPOINT`  
Mode: **LOCAL / real Unity visual-play evidence required**  
Depends on: `WP-H2F-02` PASS  
Blocks: `WP-H2F-GATE`

## Claim

The frozen candidate stack works as one coherent Juego2 production baseline when rendering, worldbuilding, traversal/navigation and character presentation are exercised together, survives the accepted H1 public lifecycle according to the H2F-02 state-classification boundary, and a fresh author/agent can use the prescribed Juego2-side surfaces without turning plugin-private state into canonical authority.

## Fixture rule

Use a bounded **`H2F_INTEGRATION_FIXTURE / NON_KEEPER`** fixture.

It may reuse admitted ART-01 `PREFOUNDATION_INPUT` assets, dimensions, composition rules and representative conditions, but it must be visibly recorded as a compatibility fixture. ART-01 does not need to have passed. The fixture cannot satisfy ART-01 readiness, CITY-07 keeper acceptance, replace the retained CITY seed or become a backdoor redesign of CITY semantics.

The fixture should be as small as possible while exposing cross-tool failures: one short exterior route/street or path, meaningful level/edge treatment, one threshold/window/interior-depth condition, bounded nature, one player route and one representative humanoid.

## PASS-before-work acceptance contract

- **Positive claim:** the selected H2F stack coexists on one real Unity fixture, remains valid through the accepted H1 materialize/observe/reconcile/rematerialize/clean-rebuild lifecycle, and supports the complete minimal authoring/play path needed before CITY-07 commits keeper content.
- **Mandatory positive evidence:** (1) continuous third-person capture/inspection of the integrated fixture; (2) rendering/material evidence under the frozen URP baseline; (3) selected linear/terrain/nature/edge tooling exercised together; (4) player camera/input + collision/navigation exercised; (5) one actual Quaternius humanoid using the selected animation/retarget baseline plus any adopted rigging/IK correction; (6) one fresh-author/agent operation using the approved adapter/preset/public path; (7) the composed H1 lifecycle transcript and before/after state witnesses required below; (8) bounded profiler snapshot under the predeclared diagnostic oracle below; (9) issue ledger distinguishing stack blocker from later art/performance polish.
- **Negative gates:** FAIL if each package only works in its own demo scene; if the fixture hides incompatible materials or tools; if a plugin-private object graph becomes the only authoring API; if an AI directly mutates Unity/plugin state while presenting that as canonical Arkus authoring; if visual evidence is editor/top-down only; if required selected foundation state is lost, falsely classified as unsupported drift or requires undocumented hand repair after the H1 lifecycle; if an enumerated performance pathology occurs; or if this fixture is promoted as ART-01/CITY-07 keeper acceptance.
- **Non-claims:** no ART-01 readiness/PASS, no final keeper level, no whole-town performance, no H3 routine/schedule semantics, no shipping frame-rate budget and no final ART-02 polish.
- **Allowed residuals:** visual tuning and content breadth that do not call the selected toolchain choice into question; ordinary profiler numbers/optimization opportunities that do not meet an enumerated pathology; deferred categories already recorded by H2F-01.
- **Evaluation method:** human third-person visual/play inspection + bounded machine-verifiable configuration/navigation/identity checks + composed H1 public-lifecycle proof + diagnostic profiler evidence + fresh-author transcript.
- **Consumed predecessors:** H2F-02 exact adoption and lifecycle-classification matrix, ART-01 `PREFOUNDATION_INPUT` source/demand/assembly truth and accepted H1 canonical→Unity/reconciliation/rebuild authority.

## Composed H1 lifecycle proof

H2F-03 must execute one effective public lifecycle with the **entire selected H2F stack present in the fixture**, rather than merely proving that the scene opens in Unity.

Use the accepted H1 public paths and evidence surfaces; do not create an H2F-only surrogate lifecycle. The composed proof is:

```text
clean/restored accepted project state
-> materialize the bounded fixture with the selected H2F baseline present
-> observe through the accepted H1 observation path
-> perform one bounded legal change that exercises the accepted reconcile path
-> reconcile through the accepted H1 public boundary
-> rematerialize
-> remove the H1-defined generated Unity outputs / perform the accepted clean-rebuild procedure
-> rebuild/rematerialize from admitted source state
-> reopen and exercise the same fixture
-> compare required selected foundation state against the H2F-02 lifecycle matrix
```

The reconciled change must be small and deliberately inside accepted H1 authority. It exists to prove composition, not to give H1 ownership of plugin-private realization semantics.

Evidence must show, for every material state family in the H2F-02 lifecycle matrix, which one of these occurred exactly as declared:

- H1-managed projection state was observed/reconciled/rematerialized under the already accepted H1 contract;
- retained realization sidecar/prefab/preset/project state remained present and was not falsely surfaced as unsupported canonical drift;
- generated/transient state was disposable and was deterministically reconstructed or re-baked by its documented restoration step;
- manual/external lawful input was provisioned only through the declared restoration path.

At least one concrete witness from every lifecycle class actually present in the selected stack must be captured before and after the cycle. The final integrated fixture must still render, traverse/navigate and animate the representative humanoid after clean rebuild.

A mismatch is a **causal compatibility blocker**: route it to the selected H2F boundary/tool decision, or to H1 only if effective evidence contradicts an already accepted H1 guarantee. Do not patch the fixture manually and call the lifecycle compatible.

## Fresh-author / Astra trial

A fresh capable author/agent receives only the accepted H2F/ART/H1 public documentation and fixture brief needed for the operation.

It must perform one bounded operation relevant to future keeper work, for example:

```text
inspect admitted realization profiles
-> discover legal route/path/edge/nature options
-> request one bounded semantic/local change through the accepted Arkus path where canonical world intent is involved
-> materialize/use the selected Unity-side profile
-> inspect the result
-> prove unrelated fixture content was not silently regenerated
```

When the operation is purely downstream visual tooling with no canonical semantic change, direct use of the documented Unity-side adapter/preset is allowed, but it must remain clearly classified as realization state rather than canonical world truth.

This is a foundation-authoring trial, not the ART-01 fresh-author composition smoke test. Passing H2F-03 does not prove that the final ART-01 representative benchmark is `KEEPER_READY`.

## Performance sanity — predeclared diagnostic oracle

Profiling is **diagnostic by default**, not a shipping budget and not a subjective “looks slow” gate. Before capture, record the comparison context so later runs are interpretable:

- machine/CPU/GPU/RAM identity;
- Unity/editor or player mode used;
- fixture revision/candidate SHA;
- resolution and active quality/URP tier;
- camera route/traversal used;
- warm-up procedure and capture duration;
- whether GPU timings are available/reliable in that mode.

Record at minimum:

- CPU/frame timing context;
- GPU/render timing where available and meaningful;
- draw-call/batch/triangle or equivalent scene-complexity indicators;
- memory snapshot or summary;
- selected tool-specific warnings/errors.

**Ordinary numeric profiler results do not by themselves FAIL H2F-03.** They become optimization/residual evidence unless one of the following explicit foundation pathologies is reproduced and causally attributed to the selected baseline:

1. fixture crash, editor/player process termination, out-of-memory, unrecoverable device/render failure or hard hang during the bounded traversal;
2. a selected foundation capability emits an uncaught exception/error on the normal fixture path and the same causal error reproduces on a second run;
3. a selected subsystem enters a runaway/repeating error or allocation condition that prevents completing the same bounded traversal twice without restart/repair;
4. a selected capability cannot run in the frozen render/platform/project configuration it was adopted for (for example unsupported-pipeline/device/runtime validation failure), so representative fixture functionality is unavailable;
5. profiler/capture evidence shows a deterministic foundation-induced stall or resource exhaustion severe enough that the bounded fixture cannot complete its prescribed continuous traversal on two clean attempts.

A pathology must name the causal capability and reproduction step. A one-off import spike, shader compilation, editor-domain reload, first-run bake, background asset import or isolated GC spike is not a blocker unless it reproduces on the normal warmed traversal and meets one of the cases above.

There is deliberately **no FPS, frame-time, draw-call, triangle or memory-number threshold for PASS** in H2F. Shipping/scale budgets belong to later performance work. This oracle exists only to stop pathological foundation choices while preventing the Worker/Reviewer from inventing new numeric gates after seeing the capture.

Do not adopt optimization middleware merely to make this tiny fixture “faster” unless one of the enumerated pathologies is causal and H2F-01's decision is formally amended.

## PASS only if all are true

- all applicable `ADOPT_NOW` cross-cutting capabilities coexist on one fixture;
- representative Quaternius content renders correctly under the frozen URP baseline;
- selected road/path/terrain/nature tools do not produce unresolved overlap/seam/traversal blockers in the fixture;
- the player can traverse the fixture with the selected camera/input/collision/navigation baseline;
- one real Quaternius humanoid demonstrates the selected retarget/animation baseline at human scale;
- the composed H1 cycle completes through materialize → observe → reconcile → rematerialize → accepted clean rebuild with the full selected stack present;
- every material state family behaves according to its H2F-02 lifecycle classification, with representative before/after witnesses and no undocumented hand repair;
- one fresh author/agent can perform one bounded operation through the prescribed boundary without hidden canonical authority;
- no unrelated accepted content is silently regenerated by that operation;
- profiler evidence is captured under the declared context and none of the enumerated foundation pathologies reproduces;
- ordinary non-pathological performance findings are classified as diagnostic residuals rather than converted into post-hoc blockers;
- all remaining issues are classified as H2F blocker, causal predecessor contradiction or permitted later residual;
- the fixture remains explicitly non-keeper and makes no ART-01 PASS claim.

## Negative gates

The acceptance-contract negative gates are binding. Package-by-package demo success without one composed Juego2 fixture is an explicit FAIL. A fixture that works before H1 materialization/reconciliation but loses or corrupts required selected state after rematerialize/clean rebuild is also an explicit FAIL, as is inventing a new numeric performance threshold during review or treating this foundation fixture as ART-01/CITY-07 keeper acceptance.
