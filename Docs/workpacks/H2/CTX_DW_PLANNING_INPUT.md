# H2 CTX↔DW planning input — product vs knowledge portability

Status: **NON-BINDING H2 PLANNING INPUT**
Depends on for stronger use: accepted `WP-CTX-DW-GATE`
Companion: `Docs/workpacks/H2/FUTURE_PLANNING_SIGNAL.md`

## Purpose

Preserve one distinction for the future reviewed H2 plan so external productization and external agent context are not accidentally treated as the same claim.

## Two independent H2 questions

### A. Product portability

Can a fresh external repository consume a versioned/public Arkus product boundary through supported contracts without patching internal Juego2/Harness implementation?

This owns questions such as package/version distribution, public schemas, compatibility promises, release mechanics and fresh-repository consumption.

### B. Knowledge/context portability

Can a fresh Worker/Reviewer in that external repository discover the material product/domain knowledge needed to operate safely without inheriting Juego2 implementation history as working context?

CTX↔DW is candidate infrastructure for this second question:

```text
external task
  → CTX control/routing
  → selective DW structured knowledge where material
  → authoritative source/public-contract open when required
```

Passing B does not prove A. Passing A does not prove B.

## Constraints inherited from accepted DW evidence

Future H2 planning should preserve unless explicitly reviewed otherwise:

- accepted source documents remain semantic authority;
- DW remains derived/rebuildable and provenance-bearing;
- generic fact/relation/provenance surfaces do not acquire CITY/PA semantics;
- semantic necessity/cardinality remains owned by the relevant consumer/domain;
- stale/missing/ambiguous provenance fails closed;
- bounded DW-04 agent/context evidence is not generalized beyond its frozen experiment;
- in-repository DW evidence does not prove fresh-repository packaging/versioning/distribution.

## External-consumer falsification targets

A future fresh-repository trial should treat the following as material failures for the relevant claim:

- success requires hidden Juego2 paths or repository history;
- CTX routes to authority that the external consumer cannot obtain through the declared product/context boundary;
- DW requires unpublished source bytes or silently stale projections;
- a consumer must patch H0/shared semantics to express its domain;
- public schema/version mismatch is hidden by copying internal harness state;
- the agent succeeds only after receiving the proving-ground history wholesale rather than through a bounded public context route.

## Final H2 composition

If `WP-CTX-DW-GATE` is accepted before H2 finalization, final H2 public/external-boundary acceptance should explicitly consume or disposition:

1. H1-GATE Unity/public-client readiness evidence;
2. product/external-consumer portability evidence owned by H2;
3. accepted DW-GATE second-consumer evidence;
4. accepted CTX↔DW knowledge/context-portability evidence.

The final gate should compose these inputs rather than rerun every predecessor proof.

## Non-claims

This planning input does not choose:

- H2 workpack names or sequence;
- a package registry or distribution channel;
- a successor repository name;
- a specific compatibility/versioning policy;
- whether CTX/DW artifacts ship inside the same package as runtime Arkus;
- whether every future consumer uses DW.

Those remain decisions for the future reviewed H2 plan using the accepted state that exists at that time.
