# H1 CTX↔DW selective-adoption plan

Status: **PLANNING INPUT / NON-PRODUCT-SEMANTIC**
Depends on for adoption: accepted `WP-CTX-DW-GATE`
Does not block: `WP-H1-03`, `WP-H1-03A`

## Purpose

Record how an accepted CTX↔DW composition should be introduced into H1 without turning context infrastructure into an artificial product dependency and without changing any H1 product workpack claim.

## Decision

`WP-H1-03` and `WP-H1-03A` continue on the existing H1 dependency chain. They do not wait for CTX↔DW synergy work.

For those authority/lifecycle workpacks, the expected route is usually:

```text
CTX → H1/H0 authoritative contracts/code/evidence
DW → NOT_MATERIAL unless concrete evidence says otherwise
```

Correct DW abstention is preferred to loading a design corpus that has no causal role in host/workspace or Editor lifecycle correctness.

## First material adoption points

### H1-04 — catalogue/identity + first real-source adoption

This is the first planned observation point because effective catalogue identity and real-source adoption introduce content/design relationships where DW facts, relations and provenance can plausibly reduce irrelevant searching.

The H1-04 product oracle remains its deterministic Unity/catalogue evidence. CTX↔DW only changes context routing.

### H1-06 — assets/prefabs

This is the second planned observation point because source-asset, prefab and managed-derivative relationships form a materially different graph from H1-04 inventory/identity.

A successful H1-04 observation is not enough to assume H1-06 usefulness; route by claim evidence.

## Later H1

From H1-07 onward, CTX classifies DW as `USE`, `OPTIONAL` or `NOT_MATERIAL` for the active claim. There is no blanket requirement to load DW.

The classification is routing advice only. A Worker or Reviewer may always open deeper authoritative sources.

## Lightweight adoption observations

Normal H1 work may record, when materially useful:

- CTX→DW classification used;
- authoritative source escalations;
- whether DW materially shortened navigation to a fact/relation/provenance anchor;
- material blockers discovered by Worker or Reviewer;
- obvious cases where DW correctly abstained;
- obvious context/cognitive-load changes.

Do not create duplicate shadow Workers or replay every workpack solely to obtain adoption metrics.

A CTX↔DW defect found during H1 belongs to the causal routing/projection owner unless the evidence actually falsifies an H1 guarantee.

## H1-GATE

The planned fresh external AI-agent trial at `WP-H1-GATE` should use the accepted CTX↔DW route where DW is material.

The fresh agent must still be free to open authoritative H1/H0/domain sources. Deterministic H1 product evidence remains the oracle; agent prose or a convenient compact answer cannot repair a missing product proof.

The trial should demonstrate the intended user experience:

```text
fresh agent
  → CTX mission/claim routing
  → selective DW knowledge when useful
  → source-open through provenance/escalation
  → public H1/Arkus operation
```

It must not assume that all H1 information has been copied into DW.

## Non-claims

This plan does not:

- add a dependency edge from CTX↔DW to H1-03 or H1-03A;
- change H1 architecture, Unity authority or workpack acceptance criteria;
- assert that DW is useful for every H1 claim;
- authorize domain knowledge to become H0/H1 generic semantics;
- make context/token savings an H1 product PASS criterion.
