# WP-H1-06 — Asset/prefab realization + managed derivatives

Status: PLANNED / NOT_STARTED
Class: FOUNDATIONAL
EXECUTION_REQUIREMENT: LOCAL_UNITY_REQUIRED
Depends on: `WP-H1-05` PASS
Blocks: `WP-H1-07`

## Objective and central claim

Resolve logical catalogue bindings into truthful Unity asset/prefab relationships, instantiate source prefabs without overwriting them, and create only explicitly bridge-managed prefab derivatives inside the accepted generation boundary.

## WHY_THIS_BOUNDARY

Scene graph publication is already accepted by H1-05; this WP adds a distinct asset/prefab authority and reference-fidelity claim. Component property semantics are kept out because their adapter universe and error cases differ. Asset and prefab handling stay together because Unity prefab identity is an asset relationship, not a separate authority.

## Inherited guarantees

H1-04 catalogue identity and accepted Quaternius Source baseline, H1-05 generation/publication, H1-01 logical asset dependencies and H0 canonical authority.

## New guarantees owned

- source assets/prefabs are read-only catalogue inputs;
- prefab instance/source/nested relationship is retained in normalized observation;
- managed prefab derivative identity, lineage and generation receipt;
- missing/wrong-type/rebound logical asset diagnostics;
- asset changes cannot silently change the canonical selection.

## Explicitly not re-proved

Catalogue completeness, scene publication mechanics, arbitrary components, H1-04 source-license/adoption acceptance or Unity YAML byte stability.

## Allowed scope

PrefabUtility/AssetDatabase use inside managed roots, source-prefab inspection/instantiation, managed variants/derivatives, mesh/material/clip reference wiring needed by the accepted H1 slice, using the H1-04 approved Quaternius Source wherever the relationship represents game content.

Synthetic repository-owned prefabs/materials remain allowed only for harness-specific causal negative controls or bridge-marker mechanics that cannot be meaningfully represented by production source content; they must not replace available Quaternius game-art shapes.

## Forbidden scope

Overwriting source/imported assets, arbitrary asset transformation factory, Addressables/bundles, asset-store automation, gameplay, treating prefab contents as canonical state, adopting a competing substitute production-art source, or fabricating wall/roof/door/window/prop production assets when the accepted Quaternius Source baseline supplies those shapes.

## Architecture / authority boundary

The canonical binding selects a logical catalogue ID. The catalogue resolves it; the bridge realizes it. Source asset bytes/native IDs remain external inputs recorded by catalogue fingerprint and receipt. Quaternius source assets remain read-only and replaceable behind logical catalogue identity.

## Acceptance criteria

- source prefab and nested relationships are inspectable and preserved after save/reload;
- source files remain byte/semantic unchanged by materialization;
- managed derivatives exist only under managed roots with explicit source lineage;
- missing/incompatible/rebound logical IDs block truthful publication with stable diagnostics;
- replacing a catalogue mapping changes catalogue/plan evidence but not canonical world hash;
- repeated materialization is semantically idempotent;
- deleting generated derivatives and rebuilding reproduces the normalized relationships;
- the production-intent prefab/material relationships exercised by the accepted content shape come from the H1-04 Quaternius Source baseline rather than locally authored substitute art.

## Deterministic proof / evidence

Use an accepted Quaternius Source nested-or-composed prefab relationship and shared material where the source distribution provides the required shape, plus one distinct bridge-managed derivative. Observe effective prefab/source/nested links before/after reload, protect source hashes and compare generation observations. Harness-only synthetic fixtures may supplement causal controls but do not satisfy the production-content portion of the claim.

## Causal negative-conformance classes

- source prefab overwritten;
- prefab instance flattened while parity still reports success;
- nested/source lineage omitted;
- wrong asset type accepted;
- missing logical asset silently replaced by a default;
- generated derivative outside managed root;
- source mutation changes canonical hash or is journaled as canonical authoring;
- accepted Quaternius production asset is silently replaced by a fabricated substitute while relationship tests remain green.

## Content-shape probe

Required. Use wall/roof/door/window/prop relationships from the accepted Quaternius Source baseline wherever those source shapes are available; a lone primitive or locally fabricated substitute production-art prefab is insufficient. Synthetic harness-only fixtures are permitted only for proof mechanics/negative controls that are not game-art stand-ins.

## Dependency / IP implications

No new external art adoption is expected here: this WP consumes the exact Quaternius Source baseline accepted by H1-04 and must preserve its distribution/license boundary. Any additional source item needed beyond that accepted baseline must be added to the adoption record under `DEPENDENCY_IP_POLICY.md` before use. Source assets remain read-only.

## Residual risks

Complex model importer settings, broad art transformation, wardrobe/vehicles, full Quaternius coverage and shipping asset delivery remain outside scope; H1-11 later expands the accepted source slice for representative end-to-end conformance.

## Exact predecessor reopen condition

Reopen H1-04 only if effective Unity identity proves its catalogue mapping or accepted source baseline false/inapplicable. Prefab realization defects remain H1-06.
