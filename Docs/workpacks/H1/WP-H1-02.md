# WP-H1-02 — Reproducible Unity project + toolchain baseline

Status: PLANNED / NOT_STARTED
Class: FOUNDATIONAL TOOLCHAIN
EXECUTION_REQUIREMENT: LOCAL_UNITY_REQUIRED
ORCHESTRATION: WORKER_SELECTED

## Objective and central claim

Create the minimal Unity project substrate on an exact Unity 6.3 LTS patch with pinned packages, Force Text serialization and reproducible batchmode tests, while keeping H0 kernel assemblies engine-neutral and editor binaries out of the repository.

## Execution decomposition

The Worker may own H1-02 end-to-end from Chat, Codex, Work or another authorized capable Worker environment. Remote preparation is **not** mandatory. The chosen environment must still obtain the exact effective Unity/toolchain evidence required below; if it cannot, the Worker may switch authorized environment or delegate only the required execution slice under `H1_REMOTE_LOCAL_EXECUTION.md`.

A Worker with direct access to the required Unity/toolchain may implement, execute, interpret evidence, repair, pre-review and freeze without creating `LOCAL_EXECUTION.md` merely to satisfy process ceremony. Single-writer, exact-SHA/evidence binding, canonical PR/branch ownership and independent Reviewer requirements remain unchanged.

The staged remote/local handoff remains a valid optional execution mode. When chosen, the Worker commits the product/code/configuration state as `EXECUTION_BASE_SHA`, persists the closed execution manifest separately, anchors the resulting `MANIFEST_COMMIT_SHA`, delegates only the declared effective Unity actions, and verifies the resulting product/evidence chain before closeout. Codex local may be that delegated executor, but it is not required to be one when the active Worker itself can run the necessary editor/toolchain.

Any H1-02 round already started under the earlier mandatory `REMOTE_PREP -> LOCAL_EXECUTION -> REMOTE_CLOSEOUT` protocol may be completed exactly as started. Its evidence remains valid if the actual SHA chain, mutation allowlist, editor/toolchain fingerprints and effective results satisfy that contract. This orchestration relaxation alone does not require a rerun or invalidate prior in-flight evidence.

## WHY_THIS_BOUNDARY

Toolchain reproducibility, package/IP adoption and project layering can pass or fail before any bridge authority exists. Mixing them with host policy or materialization would make editor/package failures obscure semantic review. Splitting each package is administrative fragmentation, so the whole baseline remains one WP.

## Inherited guarantees

HK00 reproducible build discipline, HK00A dependency/IP and anti-lock-in rules, H0 engine-neutral project graph and HK-GATE authorization to begin Unity work.

## New guarantees owned

- exact Unity editor version and install fingerprint;
- locked minimal package graph and exact license/adoption records;
- reproducible project open/compile/EditMode test in batchmode;
- Force Text and visible `.meta` identity policy;
- assembly-definition direction preventing Unity dependencies from entering H0 assemblies;
- one canonical non-interactive batch launch recipe exposing the exact bootstrap inputs later bound by H1-03A;
- chosen render-pipeline baseline for the retained project.

## Explicitly not re-proved

H0 .NET build closure, canonical semantics, bridge contracts, asset identity or materialization.

## Allowed scope

Unity project settings, `ProjectVersion.txt`, package manifest/lock, assembly definitions, minimal bootstrap/test code, canonical local invocation script and dependency records.

## Forbidden scope

Bridge public capabilities, scene production, imported third-party art, gameplay, materialization logic, arbitrary package growth or committed Unity editor/cache binaries.

## Architecture / authority boundary

The Unity project may reference compatible Arkus `netstandard2.1` assemblies through reviewed adapter assemblies. No `UnityEngine`/`UnityEditor` reference may flow back into canonical projects.

## Acceptance criteria

- an exact 6.3 LTS patch is selected from official releases and recorded;
- a clean local checkout opens and runs the canonical batchmode EditMode suite without prompts;
- package versions/resolution are locked and the render pipeline/test framework are explicitly justified;
- Force Text, visible meta files and deterministic project settings are committed;
- editor-generated caches/build outputs remain ignored;
- project/assembly graph proves H0 projects have no Unity dependency;
- the canonical launch recipe fixes the project argument shape and Arkus batch entry-point identity without exposing either as public request authority;
- a second clean project import produces the same effective package/assembly inventory.

## Deterministic proof / evidence

Record exact editor/package/platform fingerprints, clean-import commands and two effective batchmode inventories. A small editor-open smoke may be used, but the oracle is effective compilation/test/package state.

All final evidence must be bound to the candidate under `EXECUTION_RECEIPT_PROTOCOL.md` and the selected Worker execution mode. If the optional delegated-execution mode from `H1_REMOTE_LOCAL_EXECUTION.md` is used, additionally prove its non-self-referential chain: declared `EXECUTION_BASE_SHA`, externally anchored `MANIFEST_COMMIT_SHA`, recorded `PRODUCT_RESULT_SHA`, externally anchored `EVIDENCE_COMMIT_SHA`, complete changed-file inventory, mutation allowlist compliance and final-candidate ancestry. The manifest commit must be a manifest-only direct child of the execution base; the evidence commit must be result-summary-only and a direct child of the recorded product result. Both external anchors are valid only after the referenced commit has been pushed and verified as canonical remote branch HEAD.

A single-environment Worker that does not use delegated execution is not required to manufacture that four-SHA handoff chain; it must instead provide the ordinary exact-SHA execution receipt/effective evidence required by the repository protocols and this WP.

## Causal negative-conformance classes

- package lock or exact editor pin removed;
- Unity reference introduced into a canonical assembly;
- an untracked/hidden package becomes required;
- Force Text/meta identity disabled;
- batchmode requires a prompt or interactive state;
- proof reads only the declared manifest while effective resolved packages differ;
- when delegated execution is used, manifest/result evidence attempts to self-bind to the SHA of the commit that contains that same file, or the external SHA/ancestry chain does not match repository history;
- when delegated execution is used, an external handoff/result anchor is published before the referenced commit is confirmed on the canonical remote branch.
