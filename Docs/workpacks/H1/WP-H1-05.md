# WP-H1-05 — Managed scene projection + generational publication

Status: PLANNED / NOT_STARTED
Class: FOUNDATIONAL
EXECUTION_REQUIREMENT: LOCAL_UNITY_REQUIRED
Depends on: `WP-H1-04` PASS
Blocks: `WP-H1-06`

## Objective and central claim

Materialize canonical resources and Unity binding intent into a deterministic bridge-managed Unity scene graph, using staged generations so failure/interruption cannot replace the active projection or produce a false success receipt.

## WHY_THIS_BOUNDARY

This is the first effective write-projection claim: scene, hierarchy, GameObject/Transform mapping and publication. Prefab/asset fidelity and arbitrary component schemas can fail independently and remain later WPs. Removing staging/publication would leave no meaningful materialization claim, so those stay together.

## Inherited guarantees

H0 canonical identity/validation/provenance, H1-00 bridge transaction/receipt, H1-01 binding semantics, H1-03 authority, H1-03A public Editor execution/lifecycle, H1-04 identity/catalogue snapshots, and the accepted ART-01 Quaternius Source → Juego2 Derived content baseline represented by that catalogue.

## New guarantees owned

- managed scene/root/object marker and mapping contract;
- normalized scene membership, hierarchy and Transform realization;
- versioned projection plan, materialize and normalized observe capabilities published through canonical composition and therefore reference/MCP;
- staged generation with one active manifest publication;
- idempotent same-input materialization and deletion/recreation handling;
- normalized effective scene observation anchored to canonical/catalogue inputs.

## Explicitly not re-proved

Canonical transaction/journal, catalogue completeness, ART source/license/style/derivative correctness, prefab/source-asset behavior, general component reflection, Unity validation breadth or crash/power-loss durability.

## Allowed scope

Unity scene creation in fixed managed roots, managed marker component, Transform adapter, generation staging/publication/cleanup, observation and local evidence. When the content-shape scenario needs game-representative visible assets/materials, it consumes accepted ART-01 upstream/derived catalogue entries from H1-04.

Repository-owned primitives/markers remain allowed only when they are intrinsic harness proof objects, not replacement game art.

## Forbidden scope

Writing unmanaged/user scenes, changing source assets/prefabs, authoring art derivatives, canonical state mutation, gameplay components, live runtime state, navigation/physics, claiming byte-identical YAML as parity, adopting a competing substitute art source, or fabricating production-intent art to make the scene proof pass.

## Architecture / authority boundary

The active generation is chosen by the bridge manifest only after successful plan/apply/observe. Canonical state remains authoritative if no generation is active or materialization fails. Native object IDs are replaceable mapping details. Quaternius upstream and Juego2 Derived assets remain ART-owned read-only catalogue inputs; generated scene state never becomes art-source or canonical authority.

## Acceptance criteria

- one canonical object maps to one managed object in the target scene and duplicate markers fail closed;
- canonical containment plus binding data produce deterministic hierarchy/transform under the documented coordinate convention;
- create/update/delete converge to the expected normalized graph;
- a second same-input materialization has no semantic delta;
- forced failure before publication leaves prior active generation and receipt unchanged;
- deleting generated output and rematerializing yields the same normalized observation digest;
- canonical hash/journal remain unchanged by materialization;
- scene save/reload and batchmode observation agree semantically;
- reference and MCP dispatch the same composed plan/materialize/observe handlers and return equivalent normalized outcomes; Editor-bound materialize/observe phases cross H1-03A, while a portable planning phase may remain in the external host;
- any game-representative asset/material used by the content-shape scenario resolves through accepted H1-04 catalogue entries backed by ART-01 rather than a substitute production-art fixture.

## Deterministic proof / evidence

Materialize a Potes-shaped plaza/market/bar/workshop hierarchy, using accepted ART-01 source/derived assets wherever the scenario needs visible facade/material/prop content; mutate canonical binding intent through H0, rematerialize, interrupt staging, reload the editor project and compare normalized observations. Independently enumerate managed markers from the effective scene.

## Causal negative-conformance classes

- one canonical object omitted or duplicated;
- parent/transform ignored;
- interrupted staging becomes active;
- success receipt emitted before effective observation;
- materializer changes canonical hash/journal;
- stale generation presented as current;
- second apply produces semantic churn;
- materialization or observation is reachable only through a private batch script/menu/test helper and absent from composed public discovery;
- accepted ART catalogue binding is silently replaced by locally fabricated production-intent content.

## Content-shape probe

Required. The approved hierarchy includes at least three levels, siblings, a deletion and a cross-reference so a flat cube fixture cannot satisfy the claim. Game-representative visible content comes from accepted ART-01 upstream/derived assets; synthetic harness-only objects do not count as substitute art.

## Dependency / IP implications

Consumes the pinned Unity baseline and accepted ART-01 content/provenance boundary via H1-04 catalogue identity. H1-05 introduces no art source or derivative. If the scenario needs an unadmitted item, route to ART and then refresh the catalogue rather than silently substituting another art pack.

## Residual risks

Power-loss/torn-file durability, arbitrary scene size, prefab relationship fidelity, render fidelity and gameplay behavior remain unclaimed.

## Exact predecessor reopen condition

Reopen H1-00 if Unity cannot implement the accepted generation/receipt semantics without changing them. Reopen H1-04 only with concrete evidence that accepted catalogue identity is false/inapplicable; route content-source/derivative defects to ART.

## PASS consequence / next dependency

PASS unblocks `WP-H1-06`.
