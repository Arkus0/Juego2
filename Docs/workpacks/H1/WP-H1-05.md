# WP-H1-05 — Managed scene projection + generational publication

Status: PLANNED / NOT_STARTED
Class: FOUNDATIONAL
EXECUTION_REQUIREMENT: LOCAL_UNITY_REQUIRED
Depends on: `WP-H1-04` PASS
Blocks: `WP-H1-06`

## Objective and central claim

Materialize canonical resources and Unity binding intent into a deterministic bridge-managed Unity scene graph, using staged generations so failure/interruption cannot replace the active projection or produce a false success receipt.

## WHY_THIS_BOUNDARY

This is the first effective write-projection claim: scene, hierarchy, GameObject/Transform mapping and publication. Prefab/asset fidelity and arbitrary component schemas can fail independently and remain later WPs. Removing staging/publication would leave no meaningful materialization claim, so those stay together.

## Inherited guarantees

H0 canonical identity/validation/provenance, H1-00 bridge transaction/receipt, H1-01 binding semantics, H1-03 authority, H1-03A public Editor execution/lifecycle and H1-04 identity/catalogue snapshots.

## New guarantees owned

- managed scene/root/object marker and mapping contract;
- normalized scene membership, hierarchy and Transform realization;
- versioned projection plan, materialize and normalized observe capabilities published through canonical composition and therefore reference/MCP;
- staged generation with one active manifest publication;
- idempotent same-input materialization and deletion/recreation handling;
- normalized effective scene observation anchored to canonical/catalogue inputs.

## Explicitly not re-proved

Canonical transaction/journal, catalogue completeness, prefab/source-asset behavior, general component reflection, Unity validation breadth or crash/power-loss durability.

## Allowed scope

Unity scene creation in fixed managed roots, managed marker component, Transform adapter, generation staging/publication/cleanup, observation and local evidence.

## Forbidden scope

Writing unmanaged/user scenes, changing source assets/prefabs, canonical state mutation, gameplay components, live runtime state, navigation/physics or claiming byte-identical YAML as parity.

## Architecture / authority boundary

The active generation is chosen by the bridge manifest only after successful plan/apply/observe. Canonical state remains authoritative if no generation is active or materialization fails. Native object IDs are replaceable mapping details.

## Acceptance criteria

- one canonical object maps to one managed object in the target scene and duplicate markers fail closed;
- canonical containment plus binding data produce deterministic hierarchy/transform under the documented coordinate convention;
- create/update/delete converge to the expected normalized graph;
- a second same-input materialization has no semantic delta;
- forced failure before publication leaves prior active generation and receipt unchanged;
- deleting generated output and rematerializing yields the same normalized observation digest;
- canonical hash/journal remain unchanged by materialization;
- scene save/reload and batchmode observation agree semantically;
- reference and MCP dispatch the same composed plan/materialize/observe handlers and return equivalent normalized outcomes; Editor-bound materialize/observe phases cross H1-03A, while a portable planning phase may remain in the external host.

## Deterministic proof / evidence

Materialize a Potes-shaped plaza/market/bar/workshop hierarchy, mutate canonical binding intent through H0, rematerialize, interrupt staging, reload the editor project and compare normalized observations. Independently enumerate managed markers from the effective scene.

## Causal negative-conformance classes

- one canonical object omitted or duplicated;
- parent/transform ignored;
- interrupted staging becomes active;
- success receipt emitted before effective observation;
- materializer changes canonical hash/journal;
- stale generation presented as current;
- second apply produces semantic churn;
- materialization or observation is reachable only through a private batch script/menu/test helper and absent from composed public discovery.

## Content-shape probe

Required. The approved hierarchy includes at least three levels, siblings, a deletion and a cross-reference so a flat cube fixture cannot satisfy the claim.

## Dependency / IP implications

Consumes only the pinned Unity baseline and repository-owned fixture content. No third-party art adoption is permitted here.

## Residual risks

Power-loss/torn-file durability, arbitrary scene size, real prefab relationships, render fidelity and gameplay behavior remain unclaimed.

## Exact predecessor reopen condition

Reopen H1-00 if Unity cannot implement the accepted generation/receipt semantics without changing them. Ordinary Unity-specific locator/storage choices remain H1-05 implementation details.

## PASS consequence / next dependency

PASS unblocks `WP-H1-06`.
